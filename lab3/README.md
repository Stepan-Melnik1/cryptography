# Лабораторная 03 — симметричные блочные шифры (IDEA, ГОСТ/«Магма», «Кузнечик»), C++17

## Сборка и запуск

```
make            # libcryptolab.so + ./crypto (g++ -std=c++17 -O2)
make test       # тестовые векторы и round-trip
make compare    # сравнение -O2 и -O2 -flto (размер и скорость)
```

```
./crypto -Eidea IWILLBEHEREONMONDAY          # key: ... / enc: ...
./crypto -Didea 1D3B834B322E6E03294573978AD57F71AA69D3E8B9132591
./crypto -Egost IWILLBEHEREONMONDAY
./crypto -Dgost 3B1F876E70BC17B76C0A45121EF5B36C3B683FA1310A80C1
./crypto -Ekuz  "любой текст"                # Кузнечик
./crypto -Ectr-gost "текст" [ключ [nonce]]   # гаммирование (CTR); -Dctr-... для расшифрования
./crypto -Mgost "текст"                      # имитовставка (CMAC)
./crypto -T                                  # тесты
./crypto -A 20000                            # лавинный эффект
./crypto -B                                  # скорость
```

Выводы для `-Eidea` и `-Egost` с текстом из методички совпадают с её примерами побайтово.

## Проверка корректности

Совпадают со стандартными векторами: IDEA (ключ 1..8), Магма (ГОСТ Р 34.12-2015), Кузнечик (ГОСТ Р 34.12-2015),
Магма CTR и MAC (ГОСТ Р 34.13-2015). RC2 сверен с `openssl rc2-ecb`. Плюс round-trip `dec(enc(x)) == x`
на 2000 случайных ключей для каждого шифра, проверка `mulinv`/`addinv` на всех 65536 значениях, PKCS#7 и CTR
для всех длин 0..50. Прогон под AddressSanitizer/UBSan чистый, сборка с `-Wall -Wextra -Wpedantic` без предупреждений.

## Ошибки в псевдокоде методички

1. **`GOST_core`, раунд 32.** Написано `(N1, N2) = (CM3, N2)`, но потом выводится `N2 || N1`, то есть половины
   выходят в обратном порядке. Правильно: на последнем раунде обмена нет, а результат CM3 идёт в старшую
   половину (`N2 = CM3`, `N1` не меняется). С этим исправлением совпадают и стандартный вектор Магмы,
   и примеры из раздела 3.3.
2. **`IDEA_invkeys`.** Последние четыре строки `DK[48..51]` в псевдокоде набраны с отступом внутри цикла;
   они должны стоять после цикла.
3. Константы C1/C2 из задания относятся к ГОСТ 28147-89 (режим гаммирования) и в Магме не используются;
   лежат в `vars.cpp`, потому что так требует задание.

## Режимы

* **CTR:** блок счётчика = `nonce (4 байта) || счётчик (4 байта, big-endian)`, счётчик с 0; шифрование и
  расшифрование — одна функция, длина любая. Для 64-битных блоков это соответствует схеме ГОСТ Р 34.13-2015.
* **MAC:** CMAC по ГОСТ Р 34.13-2015 (блок 64 бита, R = 0x1B). Программа печатает старшие 32 бита (`mac:`),
  как в стандарте, и полные 64 бита (`mac64:`).

## Лавинный эффект (20000 испытаний, случайные ключи и блоки)

Доля изменившихся бит шифротекста при изменении одного бита ключа (идеал ≈ 50%, σ ≈ 6.25% для 64 бит, 4.42% для 128):

| Шифр | Блок | Ключ | Среднее | σ |
|---|---|---|---|---|
| IDEA | 64 | 128 | 50.00% | 6.26% |
| ГОСТ/Магма | 64 | 256 | 49.89% | 6.19% |
| RC2 | 64 | 128 | 49.94% | 6.25% |
| Кузнечик | 128 | 256 | 50.02% | 4.46% |

Все четыре шифра дают результат, неотличимый от идеального; различия — в пределах статистического шума
(для 20000 испытаний погрешность среднего ≈ 0.04%). Для плоского текста результаты те же (`./crypto -A`).
RC2 из лабораторной 02 написан здесь заново по RFC 2268 (код той работы не использовался).

## -O2 против -O2 -flto

Измерения на машине, где я собирал (у тебя цифры будут другими, запусти `make compare`):

| | -O2 | -O2 -flto |
|---|---|---|
| libcryptolab.so, байт | 31528 | 27120 |
| crypto, байт | 74648 | 70928 |
| .text libcryptolab.so, байт | 16874 | 15563 |

**Размер.** LTO стабильно уменьшает и библиотеку (≈14%), и приложение (≈5%): компилятор выбрасывает
лишнее и встраивает мелкие функции (`load32be`, `mul65537`, ...) через границы файлов.

**Скорость.** Три прогона подряд дали такой разброс (МБ/с): IDEA ECB 61–74 против 65–89, ГОСТ ECB 22–28 против
25–28, Кузнечик 7–10.6 против 6–8. Между прогонами одной и той же сборки разница получается такой же,
как между `-O2` и `-flto`, поэтому надёжного выигрыша по скорости от LTO здесь не видно. Единственное,
что повторялось во всех прогонах, — IDEA с LTO чуть быстрее или не медленнее: `IDEA_ecb_*` лежит в `modes.cpp`,
а `IDEA_encrypt` в `idea.cpp`, и LTO может встроить вызов. Для ГОСТ и Кузнечика горячий цикл целиком в одном файле,
и LTO нечего оптимизировать.
